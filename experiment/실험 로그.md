#### Q4 과적합 분석

**결론: 과적합 맞음. 단, loss 그래프에서는 안 보이는 유형.**

```
loss 기준  → 과적합 아님  (overfit/loss_gap ≈ 0)
Kaggle 기준 → 과적합 맞음  (ep250 0.94325 > ep700 0.93593)
```

**왜 loss에서 안 잡혔나:**

```
val_mAP@50 = 1.0  (에폭 200부터 포화)
              ↑
 이 시점부터 val이 과적합 감지 불능
```

에폭 200 이후 val set이 너무 쉬워져서 mAP@50 = 1.0 고정. val_loss가 계속 내려가는 것처럼 보여도 실제론 val set을 암기하는 것. Kaggle test는 다른 분포라 거기서 갭이 드러난 것.

즉, 에폭 200 이후로는 val loss가 아니라 **Kaggle score가 유일한 early stop 기준**이었던 것이고, 진짜 early stopping point ≈ 250에폭이었다.

**이 프로젝트에서 쓸 수 있는 진짜 신호:**

| 신호 | 쓸 수 있나 | 이유 |
|---|---|---|
| val_loss 상승 | ❌ | val 포화로 신호 없음 |
| val_mAP@50 | ❌ | 에폭 200부터 1.0 고정 |
| val_mAP@0.5:0.95 | △ | 느리게 올라가긴 함 |
| **Kaggle score** | ✅ | 유일한 진짜 신호 |

val set이 186장 중 20%인 ~37장 수준이라 너무 작고 쉬워서 loss 기반 early stopping 자체가 이 프로젝트에선 한계가 있다.

**추가: train_loss oscillation 심함**

초반부터 전 구간에 걸쳐 train_loss가 에폭마다 오르락내리락이 심하다. 주원인은 **batch_size=8**. 배치가 작을수록 각 배치의 gradient 방향이 들쭉날쭉해서 loss가 oscillate한다. Phase 전환 시점에도 LR 리셋으로 튀는 구간이 있다. best checkpoint 선택이 어려워지고 수렴이 느려지는 원인. gradient accumulation으로 effective batch를 키우면 안정화 가능 (batch=8 + accumulation=4 → effective batch=32).

### 공통: 제출 전 F1 곡선으로 최적 conf threshold 확인

- **시점** 각 실험의 best 모델이 나올 때마다 1회
- **방법** conf=0.05~0.90 구간에서 val F1 계산 (IoU=0.5 고정) → F1 최대 지점 = 최적 conf
- **반영** `postprocess.conf_threshold` 업데이트 후 제출 / WBF `skip_box_thr`도 동일 방식 최적화 가능
- **근거** conf=0.25는 관행적 기본값, 모델마다 최적값 다를 수 있음 → [[concepts/F1 Score]]
